# AGENTS.md

guidance for ai coding agents (claude code, cursor, copilot, etc) working in this repo. read this every session before making changes. for the full project plan and milestone breakdown, see `launcher-plan.md`.

---

## what this project is

a controller-first minecraft java launcher built with tauri 2 + rust + solid. targets macos and linux (steam deck primary). supports vanilla and fabric, with neoforge/quilt as stretch goals. modrinth and curseforge for mods. no windows support for v1. no forge support, period.

**hard rule:** `launcher-core` and `launcher-mods` must not depend on tauri, qt, or any ui framework. they are pure rust libraries. this is what makes them testable and reusable. if you find yourself wanting `tauri::AppHandle` in `launcher-core`, you're putting the wrong thing in the wrong place — refactor so `launcher-app` does the tauri bits and calls into core.

## tech stack at a glance

| layer | tech | why |
|---|---|---|
| desktop shell | tauri 2 | smaller + more secure than electron, native rust backend |
| backend language | rust | jvm spawning, downloads, hashing, file work all fit rust idiomatically |
| async runtime | tokio | standard, plays nice with reqwest |
| http | reqwest | standard |
| ipc types | specta + tauri-specta | generates `bindings.ts` for type-safe commands and events |
| ui language | typescript strict | catches bugs early; solid's types are excellent |
| ui framework | solid 1.9+ | fine-grained reactivity, small bundle, fast on steam deck |
| routing | @solidjs/router | lightweight, fits our ~6 screens |
| server state | @tanstack/solid-query | caches modrinth/curseforge api calls, deduped fetches |
| virtualization | @tanstack/solid-virtual | log view and long mod lists |
| primitives | @kobalte/core | accessible headless components (dialog, dropdown, slider) |
| styling | tailwind 3.4+ | utility-first, tokens defined in `design/tokens.ts` |
| gamepad input | gilrs (rust) | cross-platform, handles hotplug, more reliable than browser gamepad api |

## solid-specific gotchas (read these or you will write bugs)

solid looks like react but isn't. these are the patterns claude code most commonly gets wrong:

### 1. signals are functions. never destructure them.

```ts
// ❌ WRONG — destructuring breaks reactivity, the value is captured once
const { value } = props;
return <div>{value}</div>;

// ❌ WRONG — props.value is read once at component creation, never updates
const value = props.value;
return <div>{value}</div>;

// ✅ RIGHT — props is a reactive proxy, read it directly in jsx
return <div>{props.value}</div>;

// ✅ RIGHT — for signals, call them as functions
const [count, setCount] = createSignal(0);
return <div>{count()}</div>;
```

**rule of thumb:** if you see `const { foo } = props` or `const foo = signal()` outside a jsx expression or `createMemo`, it's almost always wrong.

### 2. there is no useEffect dep array. createEffect tracks signals automatically.

```ts
// ❌ WRONG — this is react thinking
useEffect(() => { ... }, [foo, bar]);

// ✅ RIGHT — solid tracks signal reads inside the effect automatically
createEffect(() => {
  console.log(foo(), bar()); // re-runs when foo() or bar() changes
});
```

if you want effect cleanup, use `onCleanup` inside the effect:
```ts
createEffect(() => {
  const interval = setInterval(...);
  onCleanup(() => clearInterval(interval));
});
```

### 3. components run once. don't put logic that needs to re-run in the function body.

```ts
// ❌ WRONG — this only runs once, on component creation
function Greeting(props) {
  const greeting = `Hello, ${props.name}`;  // captured once
  return <h1>{greeting}</h1>;
}

// ✅ RIGHT — derive reactive values with createMemo or inline
function Greeting(props) {
  return <h1>Hello, {props.name}</h1>;
}

// ✅ RIGHT — for expensive derivations
function Greeting(props) {
  const greeting = createMemo(() => `Hello, ${props.name}`);
  return <h1>{greeting()}</h1>;
}
```

### 4. use `<For>` and `<Show>`, not `.map()` and ternaries

solid's control flow components are not optional sugar — they preserve reactivity and avoid unnecessary work.

```tsx
// ❌ WRONG — re-renders the entire list on any change
{items().map(item => <Item data={item} />)}

// ✅ RIGHT — only re-renders changed items
<For each={items()}>{(item) => <Item data={item} />}</For>

// ❌ WRONG
{condition() ? <A /> : <B />}

// ✅ RIGHT — Show preserves component state better and is clearer
<Show when={condition()} fallback={<B />}>
  <A />
</Show>
```

### 5. createQuery from tanstack-solid-query takes a function returning options

```ts
// ❌ WRONG — react pattern, query won't react to query() signal changes
const result = createQuery({
  queryKey: ['search', query()],
  queryFn: () => commands.search(query()),
});

// ✅ RIGHT — pass a function so solid can track the signal
const result = createQuery(() => ({
  queryKey: ['search', query()],
  queryFn: () => commands.search(query()),
}));
```

### 6. don't reach for stores until signals fail you

`createStore` exists for nested reactive objects. for most cases, a `createSignal<T>` with immutable updates is simpler and sufficient. use stores when you have deep nested reactive state where you want to update one leaf without retriggering the rest.

### 7. refs are not signals

```tsx
// ✅ this is how refs work in solid
let myRef!: HTMLDivElement;  // use ! since solid assigns after mount
return <div ref={myRef}>...</div>;

// inside onMount, myRef is now set
onMount(() => {
  myRef.focus();
});
```

## rust conventions for this project

### error handling

- libraries (`launcher-core`, `launcher-mods`) use `thiserror` for typed errors. one error enum per module, or one for the crate if scope is small.
- the binary (`launcher-app`) can use `anyhow` for top-level error handling, but commands exposed to tauri return `Result<T, AppError>` where `AppError` is `serde::Serialize` (so it crosses the ipc boundary cleanly).
- never panic in code reachable from a tauri command. `unwrap`/`expect` only on truly impossible cases, with a comment explaining why it's impossible.

### async

- use `tokio` everywhere. don't mix in async-std or smol.
- prefer `tokio::sync::mpsc` for event channels. avoid `std::sync::mpsc`.
- use `Arc<RwLock<T>>` (tokio's `RwLock`, not std's) for shared mutable state across tasks. consider whether you actually need shared mutability first — often you can restructure to avoid it.

### file io

- `tokio::fs` for async file io.
- always write files atomically: write to `path.tmp`, then `rename` to final path. minecraft instances are user data, corrupted instance.json files are unacceptable.
- never assume file paths exist. `std::fs::create_dir_all` (or tokio equivalent) before writing.

### http

- one `reqwest::Client` per `Downloader` / api client instance. clients are cheap to clone (internal arc), expensive to create. **do not** create a new client per request.
- set timeouts on every request. default reqwest timeout is `None` which will hang forever on a stalled connection. use 30s for normal requests, longer for downloads.
- always set the user-agent header per modrinth's api guidelines: `yourname/launcher/0.1.0 (contact@email)`.

### testing

- pure logic in `launcher-core` and `launcher-mods` should have unit tests. test fixtures (sample version manifests, sample mrpack files) live under `crates/*/tests/fixtures/`.
- integration tests that hit the network or spawn java go under `crates/*/tests/` with `#[ignore]` so they don't run on every `cargo test`. document how to run them in the crate readme.
- the tauri layer (`launcher-app`) is mostly thin glue; manual testing is fine, automated e2e is not a v1 goal.

## ipc patterns

### commands

every tauri command:
1. has `#[tauri::command]` and `#[specta::specta]` attributes
2. returns `Result<T, AppError>` (never bare `T`, never panics)
3. is a thin wrapper that calls into `launcher-core` or `launcher-mods`
4. is registered in `tauri::generate_handler![...]` AND in the specta builder

```rust
#[tauri::command]
#[specta::specta]
async fn list_instances(state: State<'_, AppState>) -> Result<Vec<InstanceSummary>, AppError> {
    state.instance_manager.list().await.map_err(AppError::from)
}
```

### events

for long-running operations (launch, download, mod install), the command returns a `task_id: String` and emits events on `<task_kind>:<task_id>:event`. the frontend listens on that channel.

prefer this over having the command return a future that resolves at the end — long-running futures across the ipc boundary are awkward and don't surface progress.

### specta workflow

- add `#[derive(Type)]` to any rust type used in command signatures or events
- run `cargo run --bin launcher-app -- --generate-bindings` (or whatever script you wire up) to regenerate `frontend/src/bindings.ts`
- the generated file is checked in. if it's out of date with the rust source, ci should fail.
- do not edit `bindings.ts` by hand

## commit and pr conventions

- conventional commits style: `feat(launcher-core): add fabric manifest merging`, `fix(frontend): focus ring not visible on dark cards`, `chore: bump tauri to 2.1`
- scope is the crate or `frontend`
- keep commits focused. one logical change per commit. if you're adding a feature and also fixing an unrelated lint, those are two commits
- pr titles match the merge commit
- pr body: what changed, why, how to test, screenshots if ui

before opening a pr, run:
```
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cd frontend && npm run lint && npm run typecheck && npm run test
```

## what "done" means for each milestone

every milestone in `launcher-plan.md` has an explicit acceptance test. a milestone is done when:

1. the acceptance test passes manually on both macos and a linux box (preferably a steam deck for milestone 6+)
2. unit tests cover the new logic in `launcher-core`/`launcher-mods` where appropriate
3. no new clippy warnings introduced
4. typescript compiles with no errors in strict mode
5. the user-visible behavior is documented in a brief readme update if it affects how to use the launcher

do not start milestone n+1 until milestone n is done by this definition.

## things to escalate, not guess

when in doubt, ask the user rather than picking. specific cases:

- **anything affecting the focus model.** the controller ux is the most differentiated thing about this launcher. design changes there should be checked in.
- **adding a new top-level dependency** (especially a new framework or large library). small utility crates are fine, but anything in the stack table above changing is a discussion.
- **changing data on disk format** (`instance.json`, `accounts.json`, `settings.json`). every change needs a migration plan even pre-v1, because the user will already have instances they don't want to lose.
- **anything touching auth.** msa is fiddly and a botched change can lock users out. write tests, test manually with a real account, ask before merging.

things that are fine to just do:

- refactors within a single module that don't change public api
- adding tests
- fixing typos, lint warnings, dead code
- adding logging
- styling tweaks that match the existing tokens

## anti-patterns specific to this codebase

things i've seen agents do that i don't want here:

1. **adding tauri imports to `launcher-core`.** if a feature in core needs to emit progress, take a `tokio::sync::mpsc::Sender<Progress>` parameter. the tauri layer wires the sender to events. core stays pure.

2. **using `serde_json::Value` because parsing the real schema is annoying.** the version manifest, fabric profile json, mrpack index, etc all have stable enough schemas to type properly. typed structs catch bugs at compile time. only fall back to `Value` for truly open-ended fields.

3. **putting logic in solid components.** components should compose primitives and render. business logic goes in dedicated modules (`input/`, `api/`, etc) and gets called from components.

4. **fetching directly from the frontend.** all network access goes through rust. the frontend only talks to the launcher backend via tauri commands. this is for security (csp), testability, and offline caching.

5. **logging tokens.** `access_token`, `refresh_token`, `identityToken` should be filtered from any structured logging. if you add a new token type, add it to the filter.

6. **leaving `// TODO` without an issue.** if something's deferred, write a github issue and reference it: `// TODO(#42): handle the case where...`. comments without issues rot.

7. **breaking the rule that mac and linux are the only supported platforms.** don't add windows path handling. don't import `winapi`. don't pull in dependencies that only build on windows. it's fine if code happens to work on windows, but no effort is spent supporting it in v1.
